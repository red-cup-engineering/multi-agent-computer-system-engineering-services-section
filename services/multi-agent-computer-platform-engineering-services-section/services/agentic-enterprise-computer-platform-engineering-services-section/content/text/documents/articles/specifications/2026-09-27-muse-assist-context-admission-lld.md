## Receiving effect and selected realization

This derives from L-I01–L-I03 and L-I08, preserving H-I1–H-I4. An authenticated person selects an admitted personal context and performs a permitted action there. Before any request content is retained, personal evidence is read or inference is invoked, the host establishes the exact context, current participant permission, journal and applicable use policy. The useful effect is access to one's authorized work; authentication alone does not supply it.

Use the existing instance composition, typed operations, witnessed dispatch and causal journal. Add one preparation boundary to the shared dispatch path so every transport can obtain the same scoped runtime. The application declares the need for personal context and consumes scoped ports. It must not add a notebook, permission cache, task store, private scheduler or second execution loop. Retire the early unscoped arrival path for personal operations and the use of a process-wide filesystem binding by their handlers. Ordinary institutional and process operations retain their own explicit authority contracts.

## L-C01 — Operator-admitted context definition

A context is deployment configuration under an admitted operator's custody, not a user-uploaded authorization document. Its versioned definition contains the exact context id, accountable owner, journal identity, participant permissions, allowed capability references, retention policy and disclosure policy. It carries a content-bound definition reference and a current revision under the host's admitted configuration source. A string claiming an issuer, a content digest without provenance, or a record admitted through an arbitrary write operation is not configuration admission.

Context ids and principal ids are exact bounded strings under the shared canonical-data envelope; do not normalize aliases into authority. The request selects only the context id. It cannot supply owner, journal identity/root, participant list, provider, policy, effective principal or a positive authorization verdict. The selected context's owner does not automatically become the caller. An owner and other participants must have explicit applicable permissions; role labels alone grant nothing.

Participant permissions distinguish message admission, work/history reading, correction, decision, cancellation, result assessment and artifact reading. Each permission is an exact action, not a string prefix, wildcard or global public capability. A decision permission still requires authority over that exact effect proposal. Assessment still requires the independent receiving role and assignment/result correspondence in L-I06/L-W07. Context access cannot confer an institutional office, calendar/message credential, publication right or spending grant.

The host intersects context permission, context capability scope, current operation standing and any required effect/receiver authority. A positive result from the existing `can()` over unfiltered assertions is insufficient: that function accepts schema-valid issuer strings and public/wildcard grants without verifying their provenance. Keep its useful standing fold only where a trusted admission path has already established the relevant authority and scope; do not treat the fold as an issuer verifier.

## L-C02 — Current host resolution and storage scope

The Systems host supplies the context source and scoped runtime factory through the existing application/instance binding. The application does not read environment variables, arbitrary paths or a mutable user-controlled catalog to obtain authority. Resolve the current admitted definition for each request; do not retain positive permission in a process-wide cache. Read failures, conflicting configuration, unsupported policy, stale revision, unresolved identity or unknown participant fail closed.

For the initial personal realization, each context privacy boundary owns a distinct admitted journal identity and host binding under L-H01–L-H06. Multiple participants may share that one context according to its permissions. Two differently scoped contexts must not silently alias the same raw journal/root. This is a storage binding within the shared journal implementation, not a journal implementation or service per person. Migration of existing work into a context requires attributable ownership/use evidence; a filesystem directory name is not sufficient authority to classify its content.

Runtime handles expose context-scoped interaction admission, work reads, exact artifact resolution and bounded inference/effect proposal ports. They do not expose a root path, general `readAtRoot`, unrestricted `openJournal`, the complete operation catalog, credentials or arbitrary network execution. The host may possess such capabilities; it must not pass them to the personal operation as its access interface. Content-address knowledge by itself confers no read permission. Cross-context evidence or artifact use requires an explicit authorized disclosure/import and preserved provenance, never a fallback global search.

Journal host identity and context-definition identity remain separate. Resolving a context must verify its admitted journal binding; inventing a journal from a context id or server package name is prohibited. Journal failures retain their storage-unavailable meaning internally and do not become an empty history or a false unknown-context result.

## L-C03 — Prepare before retaining arrival or attempt content

A personal operation declares that it requires personal-context admission and identifies the context selector in its closed input schema. The operation declaration is trusted installed metadata, not a flag supplied in a request. Missing host support for that declaration is a refusal, never process-mode fallback.

The shared preparation sequence is:

1. Establish the transport principal. HTTP uses L-A01–L-A04. A local fixture must be explicitly bound to its fixture actor; the mixed MCP host/user channel needs the distinct call provenance described below.
2. Resolve the trusted operation declaration and decode/validate the bounded input in memory. Reading inbound bytes for validation is not a private journal read or permission to retain them. Do not invoke inference to select the effective principal, context or authority.
3. Resolve the current context selected by that input and check the requested action, capability and use-policy intersection for the principal. Confirm exact context/journal identity and available scoped runtime without reading unrelated private content.
4. Bind the admitted input, principal, operation reference, context-definition revision and scoped runtime as one internal prepared invocation. This is an in-process result from the trusted preparation boundary, not a JSON token a client can manufacture or a reusable grant.
5. Only then retain the permitted arrival/attempt material and enter the existing witnessed dispatch/proposal/attempt boundary using that scoped runtime. Preserve exact input and cause correspondence required by L-I02/L-I03 and durable retry uniqueness; preparation does not itself admit a second intent.

The same prepared invocation must determine transport arrival, RPC attempt, authorization, handler context and outcome destination. Do not authorize context A and then retain/execute against process root B. A second parse, changed request body, changed context selector or changed operation invalidates preparation. Do not merge an admitted scoped runtime over options that leave a hidden unscoped witness, feed, inference provider or resource reader reachable.

The existing generic RPC ordering admits an attempt before authorization, and HTTP/MCP route code can admit full request content earlier still. A check only inside `museAssistOperations.run` is therefore too late. Personal preparation must precede those calls. Preserve useful coarse operational refusal observations only under an explicitly admitted host diagnostic policy, excluding request body, attachment data, private identifiers and unverified principal claims; no new diagnostic store is required by this LLD.

## L-C04 — Scope survives every route and use

HTTP operation routes, MCP tools, CLI commands, work queries, artifact resolution and any personal subscription must enter the same preparation capability. A generic HTTP resource handler, feed endpoint, guest chat-completions route or WebSocket claim session cannot stand in for it. The existing raw `/data/**` resource is not a personal artifact resolver. Personal mounting must omit/replace those unscoped routes through the shared server composition; merely hiding links in the UI is insufficient.

For MCP, distinguish an explicitly authenticated user call from a trusted host's own service call at the host boundary. User payload `_meta` is not proof by itself. Preserve initialization and service discovery under an explicitly admitted control/service context; absence of user metadata cannot choose the host account for a personal operation. The ops host currently uses both categories through one client, so its actual callers must migrate with this boundary. Do not make public HTTP honor the stdio-only metadata convention.

Transport disconnection does not renew permission, cancel work or settle a result. Each later asynchronous use obtains current authorization for its exact purpose. Check current context/authority immediately before reading or disclosing private material, retaining a newly admitted command, invoking inference or dispatching an effect. A changed revision causes re-preparation or a named waiting/refusal condition. A completed read may exist in host memory after revocation, but it cannot authorize later inference, disclosure or execution. Already committed effects and results remain available for separately authorized reconciliation/assessment under L-I06; revocation does not erase history or manufacture non-execution.

## L-C05 — Retention and disclosure are operative policy

The context binds verified policy definitions and their admitted interpreters. Missing, unknown or unimplemented policy refuses the relevant use. Recording a policy name beside an unrestricted reader/provider is not enforcement. The fabrication order must bind the exact supported policy representation and the decision points that implement it; this LLD does not invent a universal policy language or declare a production retention period.

Before initial message retention, determine whether the exact input and attachments may be retained for this context and purpose. Before inference, determine which authorized source material may be disclosed to that provider under the applicable grant. Before offering an artifact, establish exact representation, access and relationship to the request. External notification/delivery remains a separately authorized effect; returning a transport response is not authority to send messages elsewhere.

Corrections and use restrictions preserve causal attribution. Withdrawal prevents later uses within its scope; evidence preservation and any separately applicable retention obligations follow L-I06. No silent deletion, automatic external disclosure or blanket all-provider grant is introduced by context admission.

## L-C06 — Public refusals and private evidence

Unknown, forbidden and inactive contexts produce the same public `context-unavailable` refusal before private reads, inference or retention. The response must not reveal whether another person's context exists, its owner, paths, policy, grants or artifact contents. Resource/storage faults use a sanitized unavailable response, with their distinct cause kept in admitted host diagnostics where permitted. Do not convert a fault into successful empty data. These response rules do not claim constant-time behavior or eliminate all network side channels.

An admitted request's private evidence binds the authenticated principal, exact operation/input identity, context-definition revision, applied policy/grant evidence and owning journal reference. Return only the reference/projection permitted to that participant. Content digests and syntactically valid evidence locators are not independent acceptance of the permission decision.

## L-C08 — Exact installed operation metadata

The declaration property is `admission`. Its personal form is governed by `2026-09-27-muse-assist-operation-admission.schema.json` (SHA-256 fa8aed96f6142e4dedd7dcdd1e24fbbd5acd1318d31de3025995e91253dd7974). It is the closed object `{kind: "personal-context", version: 1, contextField: "context", action}`. `action` is exactly `command-kind`, `read`, or `artifact`. The domain must be a closed JSON object schema with a required string `context`. For `command-kind`, the domain must require `kind` and validate the five L-I02 command variants; the requested permission is exactly the validated kind: `message`, `correction`, `decision`, `cancel`, or `assessment`. `read` and `artifact` select those exact permissions, without consulting a request-supplied role or action. Queries and artifact requests retain their own closed input contracts. No generic JSON-pointer resolver, arbitrary action expression or application-specific authorization callback is introduced.

The operation constructor must validate the metadata, retain it on the runtime operation, and include it in the content-addressed declaration and every persisted/serializable operation descriptor. Changing context admission or action therefore changes the operation reference. Schema-addressed operation discovery must preserve the declaration. Unsupported versions, malformed metadata, missing domain requirements, or an installed descriptor that discards admission refuse installation. Discovery of an operation is not permission to invoke it. `lazyOperation` must match the loaded operation to the authorized descriptor by reference, verb, admission metadata, domain/codomain schema bodies and referenced schemas, boundary formats and effects before calling its executor. A same-name executable is insufficient. Descriptor rehydration must refuse different schema bodies sharing an address instead of silently reusing the first cached contract. Operation aliases retain admission metadata and derive a new declaration reference for the new verb; argument binding and projections cannot discard or weaken admission. Personal family loading must obey L-C10's restriction on captured host capabilities before any factory is evaluated. The operation declaration still identifies the contract rather than proving executable implementation bytes; fabrication evidence binds those separately.

Absent `admission` preserves an existing non-personal operation's declared authority contract. It is not a compatibility escape: personal surface composition accepts only the admitted personal operation references selected by the instance, rejects a personal route targeting an operation without this metadata, and never supplies personal data ports to an unmarked handler. Internal personal work uses separately admitted assignment/provider authority through the same scoped host capability; it cannot borrow the owner's identity or a legacy process operation to bypass personal context restrictions.

## L-C09 — One prepared invocation and one consumption

The shared Systems RPC boundary owns `prepareInvocation(runtime, candidate)` and `dispatchPrepared(runtime, handle)`. These are intended interfaces to fabricate, not existing exports. Existing `dispatch(runtime, candidate)` remains the common convenience entry: it prepares then consumes. Transport paths that must retain an arrival first call preparation themselves, admit that arrival through the prepared boundary, and consume the same handle. They must not prepare again after retaining against some other runtime.

Preparation resolves the exact catalog operation; checks reference/verb correspondence and its closed input domain; snapshots canonical JSON input, arguments, principal, request identity and caller provenance; and applies L-C03. Reject unsupported JSON/accessor/prototype material at the admitted canonical-data boundary. Deep immutable snapshots prevent later caller mutation. Validation occurs without invoking the operation body or touching a private journal. For personal operations, missing context host support refuses before `runtime.witness.admit`, `runtime.authorize`, arrival admission or `operation.execute` can access process-wide ports. Operation standing used during preparation must be available from an admitted non-personal catalog decision or the selected scoped authority port, never by consulting unrelated personal records.

A successful result is `{kind: "prepared", handle}`. The handle is opaque, non-serializable authority: an empty frozen identity object whose private state is held by the preparing boundary, bound to that exact host runtime identity and exact operation object. It must not contain an externally writable runtime, witness, root or invocation. A copied object, JSON reconstruction, handle from a different runtime, or already consumed handle is rejected. Private state binds the canonical invocation, context revision, policy evidence, scoped ports and any subsequently admitted arrival evidence. A content hash alone cannot create a handle. The runtime may not mutate or replace the selected operation/catalog between preparation and consumption; a mismatch refuses.

`dispatchPrepared` claims the handle synchronously before its first await. Two concurrent calls cannot execute it twice. An optional arrival-admission method on the same boundary also reserves its phase before awaiting and accepts no replacement request body, operation, principal, context or destination. Dispatch cannot race ahead of pending/failed arrival admission. The prepared boundary derives the retained arrival from the validated snapshot and its applicable retention policy. An arrival can add its exact causal references to the final invocation without changing semantic input or operation. The existing invocation identity omits `causes`; this is a causal enrichment, not permission to change the semantic identity. A request identity required before arrival is derived from the bounded admitted request material, not invented from a later receipt. L-I02's durable `(context, principal, requestId)` command uniqueness remains authoritative across retries and fresh handles.

Failed preparation returns `{kind: "refused", code}` with a bounded public code: `invalid-request`, `authentication-required`, `context-unavailable`, or `service-unavailable`. Private failure detail does not enter a receipt, stderr or transport error by default. `dispatch` adapts this to its public obstruction shape with no private evidence claims and no witness append. Unknown/forbidden/inactive context cases use the same code and public description. Framework exceptions and policy/storage failures cannot fall back to the original runtime.

A prepared handle is a short-lived execution capability, not a durable grant. Claiming it once does not authorize every subsequent use. Before every private read, retention, inference disclosure, artifact response or external effect, the scoped port rechecks the current context revision, action and applicable policy/authority at its own execution boundary. A later worker resumes from journal evidence and a newly admitted assignment/current authority, never by persisting or reviving this handle. Reconciliation of a previously committed effect follows its separately authorized path.

Apply the complete JSON_RESOURCE_ENVELOPE, including its 1,048,576-byte aggregate source/canonical bound, before parsing/allocation. This initial fabrication supplies loading/verification, not an automatic maintenance writer or context migration. Reject duplicate context ids, duplicate journal bindings, unresolved roots and conflicting identities before making personal operations callable. The domain definition never exposes the settlement root to an application or caller. Journal relocation/reassignment requires the existing separate custody/migration contract.

A context definition has `id`, `owner`, `journal`, `active`, `operations`, `permissions`, `retention`, and `disclosure`. Each permission is an exact `(principal, action, operation)` triple. Reject duplicate triples and references outside that context's operation set. A permission's action must agree with the installed L-C08 admission selector or one of its five command kinds. Empty permissions are permitted and grant nobody access. There are no role inheritance, wildcard, prefix, public-holder or owner shortcuts. Retiring a context uses `active: false`; retaining its journal is not continuing authorization.

## L-C12 — Initial retention interpreter

The sole initial retention body is `{kind: "causal-evidence", version: 1, disposition: "retain-until-authorized-disposition", maxCommandBytes, maxAttachmentBytes}`. Limits are explicit positive safe integers selected by the admitted deployment. No production values or retention duration are supplied here. Before admission, measure the exact canonical command bytes and aggregate verified attachment representation bytes. Require both configured bounds and the existing wire/journal budgets. Count each distinct attachment representation once, while preserving every declared use/reference in the input. Unknown/unresolved/unauthorized attachment bodies refuse; do not fetch arbitrary paths or URLs to satisfy a bound.

This policy permits retention only for a command whose current context/action/operation and applicable use restrictions have passed. It permits the minimum causal arrival, decision, proposal, attempt, outcome and receiving evidence required to account for that admitted work, subject to current authority for that stage. It does not grant an unrestricted append port or permission to retain unrelated context, credentials, transport authorization headers, configuration bodies, failed unauthenticated requests, or raw unvalidated diagnostic payloads. Reconstruct a bounded semantic arrival from the prepared snapshot; do not store the original transport envelope wholesale.

The interpreter maps retention checks to the existing journal admission contracts and verifies each event's relationship to the exact prepared command or separately admitted work assignment. There is no TTL, automatic erasure or promise of finite retention in this policy version. If a requested context requires a maximum storage duration, erasure guarantee or other unimplemented disposition, refuse that context rather than mislabeling immutable journal retention as compliance. Withdrawals prevent subsequent uses within their scope and corrections remain causal; evidence disposal requires its separately authorized capability and cannot be manufactured by deleting arbitrary journal files. A record retained under this policy is not thereby authorized for inference or external delivery.

## L-C13 — Initial disclosure interpreter and current use

The sole initial disclosure body is `{kind: "explicit-disclosure", version: 1, participantResponse: "authorized-action", inference}`. Empty `inference` permits no provider disclosure. Every inference entry is an exact tuple of `principal`, originating `operation`, host-admitted `provider`, `purpose`, `sourceClasses` and `maxBytes`. The three initial purposes are `interpret-request`, `plan-work` and `produce-result`; they describe those existing L-I04/L-I05 work stages and confer no new work authority. Select exactly one matching entry; duplicates or multiple matching entries are invalid configuration rather than a chance to union permissions or choose a larger byte budget.

A provider identity resolves through the trusted host inference binding to its admitted endpoint, credentials and disclosure obligations. A request-supplied provider id, URL, model alias or configuration assertion cannot establish that binding. The source grants disclosure to that admitted provider for the exact purpose; it cannot prove a provider's retention/training behavior. Missing provider identity/custody evidence, unsupported required provider restrictions or unavailable binding refuses disclosure. The initial catalog must contain only provider arrangements whose stated requirements the host can actually enforce or whose external undertaking is explicitly admitted by the operator. Do not publish such admission as independently verified provider behavior.

Construct the outbound packet from exactly the granted source classes: `submitted-command` is the admitted input under its current use restrictions; `authorized-history` is context history this principal currently has `read` permission to use; `authorized-artifact` is an exact artifact the principal may currently read with the declared use; `derived-work` is attributable proposal/work evidence with currently authorized scope and dependencies. No class permits global search, another context, arbitrary graph traversal through referenced identities or use of instruction text as authority. A result derived from restricted material retains that material's applicable disclosure/use restrictions. A write-only participant cannot obtain unrelated history by causing inference to read it.

Before contacting the provider, verify every packet item and dependency is authorized for this exact purpose and source class, measure the exact UTF-8 outbound representation against `maxBytes` and provider bounds, and reject the complete packet on overflow or missing evidence. Do not truncate away contrary evidence or source attribution merely to pass the bound. Log only permitted causal disclosure evidence; do not retain secrets or duplicate the whole prompt into an ungoverned service log. Generated content remains an attributable derivation, never a grant or result acceptance.

`participantResponse: "authorized-action"` permits return of the action's allowed projection only to that request's verified principal: an admission reference for command submission, authorized records for `read`, an exact authorized representation for `artifact`, and bounded decision/cancellation/assessment receipts. Submitting a command does not automatically grant history, artifact or generated-answer disclosure. Check current permission for the returned projection immediately before delivery, including after an awaited provider response. The web entrance must apply the same rule to streamed output; disconnect or an open stream cannot preserve a revoked permission. No email, calendar write, publication, notification, webhook or other outside delivery follows from this response rule; those remain separately admitted effects under the shared proposal/attempt boundary.

Current-use authorization is the conjunction of the unchanged host source binding, exact context/action/operation permission, scoped operation standing, applicable causal restrictions and any provider/receiver/effect authority. Host source verification and entry into the scoped operation must form one local admission step without an intervening await or yielding user callback. Controlled configuration maintenance quiesces these admissions; it is not an arbitrary concurrent file edit. For causal revocation, the scoped authority/journal owner establishes the decision's current frontier at the operation's admission/reservation boundary. Once an external effect is dispatched, later withdrawal cannot assert it never happened; follow its recorded result or uncertainty to reconciliation. After any await, every new read, retention, inference request or response disclosure is a fresh use check. Final integration must demonstrate these boundaries with a permission withdrawal between preparation and use, not merely show that startup parsed a policy.
