MUSE-ASSIST / DEVELOPMENT & ARCHITECTURE

The whole path
from intent to effect.

A personal agent needs to turn a request into continuing work: select a next action, use real capabilities, handle human decisions, and preserve what actually happened.

muse-assist specializes MetroPlat for that experience. It is in early development, being prepared for an open-source release. Licensing and public package publication remain undecided.

What the repository already supplies

These are implemented building blocks, not a claim that the whole product is operating:

CapabilityExisting implementation
Operation executionMetroPlat assembles typed operation families and exposes them through shared protocol surfaces, with authority checks and recorded invocations.
Model and tool workShared inference and agent machinery supports bounded model/tool execution. The MetroPlat server also exposes inference encounters and an assigned-work consumer.
Recurring workMetroPlat’s clock admits schedules and dispatches due occurrences through the operation catalog, preserving the invoking account, attempts, and outcomes.
Personal interactionEarlier Assist applications provide evidence for sessions, conversation storage, sealed provider settings, and streaming tool-driven chat.
Knowledge and outcomesThe shared journal and agent context mechanisms retain evidence and work records. A model declaring success does not by itself settle assigned work.

The application’s responsibility

The personal experience must connect these capabilities: conversations and goals; tools and connected services; progress and interruptions; memory and artifacts; permissions and outcomes. Shared execution, schedules, and authority should retain their common implementation.

The architectural direction is to separate generic runtime mechanisms from MetroPlat’s intended platform boundary. The current Node implementation still contains mixed responsibilities. Using it for muse-assist does not make that historical concentration the target design.

Implementation status

The application composition is under development. A runnable package and its verified instructions will be described here when the complete execution path has been demonstrated. The repository’s apps/muse-assist sits beside apps/metroplat; neither a directory nor a declared endpoint proves a working assistant.

What is not established

  • A dedicated per-person computer with brokered browser control and credential isolation equivalent to Meta’s published design.
  • Complete email, calendar, messaging, shopping, and other daily-service integrations.
  • Production-ready multi-user operation, deployment, recovery, and operational support.
  • Feature parity, superior performance, or independent security validation.

These remain within the product’s scope. They are not being replaced by a smaller definition of personal assistance.

Reference platform and intended differences

Meta’s Muse is a reference for the persistent personal-agent experience. Its technical design also makes permission enforcement and credential boundaries part of the baseline.

The 561 Group’s intended contribution is an open, composable realization with inspectable knowledge and effects, explicit handling of conflicting evidence, and work that can cooperate across independently operated systems. Those differences need demonstrations, not just terminology.
