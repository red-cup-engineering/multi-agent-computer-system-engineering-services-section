## Effect and scope

This refines L-W02–L-W07 and L-I02, L-I05–L-I08: one authorized receiving effect remains the same work across concurrent requests, worker changes, interruptions and date boundaries. It selects a shared journal admission and execution boundary, not a Muse queue, task database, private tool loop or new scheduler. Personal and institutional assignments feed this boundary with their distinct authority evidence intact. Planning and independent observations remain concurrent; choosing which physical sender may perform a non-repeatable effect requires exclusive admission.

Preserve causal evidence, independently authorized receiving, existing typed RPC operation resolution and provider adapters. Replace invocation-ID-only retry identity and process-lease-only exclusion for governed effects. The old lease cannot be retained as proof of effect ownership. Unrelated operation behavior is not automatically migrated; any path exposed to the assistant that can perform a governed effect must pass the new boundary before that capability is enabled.

## Identity and journal source

**L-E01 — Separate identities.** An `effectId` is an opaque owner-scoped identifier for one intended receiving effect, established before attempts and retained across retries. A request retry identifier, proposal digest, RPC invocation ID, attempt ID and effect ID are distinct. The boundary resolves the effect's journal-owned binding to its owner, intent and personal assignment or institutional allocation; a model-supplied string establishes none of these relationships. A repeated action deliberately requested later receives a new effect, with an attributable new intent/occurrence. Timeouts never create a new effect ID.

A proposal revision can change before execution under L-W03–L-W04, retaining the prior revision and invalidating its decision. Once sending may have occurred, a replacement proposal cannot discard the unresolved effect; it first requires reconciliation or separately authorized compensation. Changing only a transport attempt does not change the proposed receiving effect.

**L-E02 — Unique journal admission.** Extend the journal's single behavioral API with create-once admission of a validated causal witness into a named admission slot. There are two uses: one slot for `(context, authenticated principal, requestId)` under L-I02, and one successor slot for `(owning journal, effectId, predecessor witness reference)`. An effect's initial predecessor is explicitly null. These are domain-separated typed tuples encoded with the existing canonical JSON contract and SHA-256; no concatenation of unescaped strings, timestamps, local paths or random attempt IDs determines their uniqueness. Exact version/domain literals and wire types belong in the fabrication order.

Admission returns `created`, `existing`, `conflict`, or `unavailable`. `created` includes the exact admitted witness reference and is returned only to the call that successfully published it durably. `existing` identifies an already admitted semantically identical command/transition; it never conveys permission to send again. A different canonical command under the request slot yields `conflict`. A different successor proposed for an occupied effect slot returns that occupied successor as a conflict for refolding, not last-writer-wins replacement. Authentication and causal/transition validation precede admission. Corruption, incomplete reads and uncertain persistence yield `unavailable`; they must not be interpreted as an empty slot.

The request comparison binds the canonical caller command, authenticated principal and context, excluding newly observed retry time. The first admitted witness retains the original admission time. Effect successors bind the exact predecessor and transition payload. Concurrent duplicate requests can therefore return the original acknowledgment even if their boundary observation times differ.

**L-E03 — Selected local persistence mechanism.** For a local filesystem journal, publish a complete immutable witness using a same-filesystem create-only hard link from a private staging file to its derived admission-slot path. Fully write and synchronize the staging file before linking; synchronize every newly created directory entry needed to reach the slot, and synchronize the containing directory after publication. Only then return `created`. An existing slot is opened and its exact witness, domain, key, causes and content identity verified. Before returning a durable `existing` acknowledgment, complete or verify the same file/directory synchronization boundary: another call may have linked the slot but not yet synchronized its directory. Completing that persistence never transfers its send permission. Do not overwrite, unlink, expire or reclaim an admitted slot because a PID died or a timeout elapsed. Failed cleanup of an unreferenced staging file cannot authorize a send.

The slot contains the canonical journal witness and its required retained content, not an independent mutable task/status record or a pointer whose target might be lost after acknowledging admission. It is an authoritative journal source. Journal artifact resolution, causal reads, subject/territory discovery, backup and compaction must include it. Segments and indexes may project it, but deleting a derived index must not delete or conceal the admission. A migration that copies the witness into an ordinary segment and then deletes the unique slot loses exclusion and is forbidden unless the replacement proves the same unique-admission contract.

This is a selected host binding, not a claim that the current atomic-write helpers provide durable publication: those inspected helpers do not synchronize files/directories. The binding must refuse use on a storage deployment whose create-only and synchronization semantics are unsupported or unverified. Remote replicas do not independently allocate slots; they route governed admission to the owning journal or a separately specified equivalent admission authority. This LLD does not invent a distributed consensus system. Models and untrusted execution must have no raw write access to the journal or its admission paths.

## Admission through sending

**L-E04 — One successor, one sender.** Fold the immutable successor chain, rejecting forks, broken correspondence, missing witnesses and unknown transition kinds. Permitted work transitions refine L-W06: proposal readiness, prepared attempt, send permission, observed outcome, reconciliation, pre-send refusal and explicit cancellation. Each transition includes its causal predecessor and authenticated actor/evidence. Receiving assessment remains a separate attributable observation and does not itself authorize a new attempt.

A prepared attempt binds the full exact proposal, stable effect ID, fresh physical attempt ID, current assignment/authority evidence and the selected adapter's retry contract. The current process may request send permission only after preparation is durable, current authority/preconditions are re-evaluated and the adapter is ready. A send-permission successor reserves the sole dispatch right for that attempt. Only the live call receiving `created` for that permission may hand the bound command to the adapter, at most once. Neither `existing` nor reading a prepared/permission record after restart transfers that dispatch right. A failure whose publication outcome is uncertain forbids dispatch by that call.

Known cancellation, supersession, decision withdrawal or revocation before send permission refuses the send. Cancellation and send-permission transitions for the same effect compete for the same predecessor slot; the winner determines their causal order. If cancellation follows permission, report that the action may already have been sent and preserve recovery work. Do not promise retroactive cancellation of an in-flight command. Grants outside this journal must be checked through their admitted authority source immediately before permission; unreachable, expired or insufficiently fresh authority refuses. Such a check does not promise atomic revocation across independent external systems.

**L-E05 — Adapter capability boundary.** Only an operator-admitted adapter may turn a permitted proposal into external effects. Its contract identifies operation/version, input/destination/disclosure correspondence, bounded credentials and egress, response evidence, timeout behavior, and exactly one supported recovery mode: receiver idempotency, authoritative reconciliation, or no automatic recovery. Inference can propose an operation but cannot select credentials, override the retry mode or call a side-channel provider. An adapter declaration without demonstrated enforcement is insufficient for capability admission.

Where receiver idempotency exists, derive its key from the owning effect domain and stable effect ID; retain the exact key in prepared evidence and reuse it across physical attempts. Include receiver key scope, retention window and payload-binding semantics. A different RPC invocation must not change that key. Expired receiver retention or changed request bytes ends automatic replay eligibility. For signed EVM operations, L-P05–L-P06 additionally require exact signed transaction identity and reconciliation before broadcast/replacement; ordinary RPC receipt success is not chain settlement.

## Interruption and recovery

**L-E06 — Uncertainty retains ownership.** A durable send permission without a verified receiving observation is uncertain, including a crash before the adapter was actually called. The journal cannot distinguish the gap by guessing. A missing `dispatched` observation is not proof that no send occurred. A recovered worker may query under separately admitted read authority and append attributable receiving evidence, but may not reuse the old send permission.

For receiver idempotency, a new attempt is allowed only under the same still-valid receiver key/payload contract and current grants. For authoritative reconciliation, a positive match binds the exact prior effect; a negative result alone does not permit another send while the old sender or an already submitted command could still act. Repetition requires evidence that the old sending path and queued transport cannot later commit, and that the negative query covers the receiving system's relevant commit/visibility interval. A lease timeout or absent PID is not that evidence. Without those guarantees, or with no recovery facility, retain uncertainty for accountable receiving assessment. This deliberately prefers an explicit unresolved action to silently doing it twice.

A retry is a new prepared attempt causally linked to the prior outcome/reconciliation, selected through the same unique successor admission and current authority checks. Reconciliation and late provider responses are attributable observations; neither can overwrite earlier evidence or directly assign completion. Contradictory receiving observations remain contested and block automatic retry/acceptance until resolved by the appropriate authority.

**L-E07 — Outcome and receiving.** Persist provider observations and exact result content identity before presenting a result proposal for L-W07/L-I06 receiving assessment. If sending succeeded but outcome retention failed, retain uncertainty and reconcile; never convert witness failure to a safe-to-repeat exception. Acknowledgment, transport completion, artifact existence and independent acceptance remain distinct. Later revocation prevents new sending, while an independently authorized receiver can still assess the exact already committed result under its historical assignment.

## Integration and removal

**L-E08 — Shared route and retirement.** Integrate unique admission into the shared journal and governed RPC execution path. The personal work frontier and institutional allocation frontier supply their validated assignment variant, proposal and effect identity. Request intake uses the same journal admission capability for its retry key. Existing source readers, journal imports, compaction and result/receiver consumers must be migrated together where they touch these records. No app-owned filesystem path, process-local deduplication map, supplemental mutable task database, or second worker loop may become authoritative.

Replace the `invocation.id` adapter key only for operations admitted under this effect contract; retain explicit legacy behavior for consumers not yet migrated and prevent those legacy effect routes from being exposed to muse-assist. Keep ordinary RPC attempt/authorization/outcome witnesses as useful execution evidence, but they do not substitute for proposal-level reservation. Removal is complete only when every enabled assistant effect and retry reaches the shared enforced boundary and no old direct route remains reachable with those credentials/capabilities.

## Independent receiving evidence

Before source derivation, commit assays covering two independent processes and concurrent invocations in one process; one slot winner; identical request replay with different observation times; changed-command conflict; and date/restart recovery. Inject interruption before/after write, file sync, link, directory sync, send permission, external handoff and outcome retention. Missing or damaged authoritative content must refuse dispatch rather than appear absent. Rebuild derived indexes and demonstrate that uniqueness and exact reference resolution survive. Process termination checks do not establish power-loss durability; assess synchronization calls and state the limits of the actual filesystem environment.

Use a controlled receiving adapter that records the actual external effect independently of producer receipts. Demonstrate stable receiver keys across invocation IDs, expired key retention refusal, changed payload refusal, late sender after negative reconciliation, and unresolved recovery with neither facility. Exercise cancellation/send races, changed/revoked authority, and receiving assessment after later revocation. The whole-application acceptance still requires an authenticated ordinary personal request through a usable artifact and independent receiving, alongside preserved institutional work; these lower-level observations alone do not complete muse-assist.

## Current evidence and fabrication boundary

The inspected process coordinator admits both invocations in the [bounded observation](evidence/2026-09-27-shared-effect-boundary/coordinator-observation.json). This establishes its lack of per-effect exclusion, not an observed duplicate external action. The dispatcher currently supplies `invocation.id` as an adapter idempotency key. Segment admission explicitly tolerates racing duplicate witness lines and projects deduplicated reads; append operations and inspected atomic file helpers do not call file/directory synchronization. None of these observations is proof of the required unique durable admission. [Input paths and digests](evidence/2026-09-27-shared-effect-boundary/inputs.json) bind the inspected sources; concurrent repository changes must be recaptured before fabrication.

Downstream fabrication must close the exact witness/domain schemas, successor transition validator, canonical slot address contract, error/result signatures, journal discovery/compaction integration, affected call sites, adapter admission and host-isolation contracts. This LLD selects their behavior and persistence mechanism; it does not authorize guessing omitted wire types during code generation or claim implemented operation. Its unresolved integration details block that generation, not continued design work.
